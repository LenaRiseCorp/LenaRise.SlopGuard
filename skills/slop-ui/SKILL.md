# Interface work

The UI and A11Y patterns catch the mechanical part: a dead link, a removed focus
outline, a stacked effect, an invented number. This skill is the rest, and the
rest is judgment.

Load it when the task builds or reviews an interface. In a project with no
frontend it has nothing to say.

## The one question

Before calling a design done:

> If the logo and the product name were swapped for someone else's, would this
> still look like a decision anyone made?

If not, the output is generic. That is not fixed by removing things — see
"The filter cannot supply direction" below.

## Technique needs a reason, not a ban

Gradient, glow, glassmorphism, large shadow, rounded corners, motion, a
background grid: none of these are forbidden. What is forbidden is reaching for
one because it is what gets generated by default.

For each one used, the reason fits on one line and names a hierarchy, identity or
readability goal. "It looks modern" is not a reason. If the line cannot be
written, the decision has not been made yet.

The patterns fire on *stacking*, because stacking is the mechanical shadow of the
same failure: glow on cards and buttons and badges and borders at once is not a
hierarchy, it is a default applied everywhere.

## The filter cannot supply direction

This is the failure mode of every rule set like this one, and it is worth saying
plainly: removing generic decoration does not produce a good interface. It
produces a plain one.

If there is no stated design direction — a brand, a reference, a mood, a
`DESIGN.md`, anything — then say so and deliver a plain, labelled draft. Do not
compensate by adding confident-looking decoration, and do not present a
directionless draft as a finished design.

Ask for direction, or state the assumption you worked under.

## Sections earn their place

A section exists because the product's content needs it. These are the ones that
usually arrive because a template had them:

hero with a two-button pair · three feature cards of identical weight · "How It
Works" in exactly three steps · a logo bar of companies that are not customers ·
a bento mosaic · a fake terminal window · three pricing columns with the middle
one highlighted · a four-column footer

Any of them can be right. Each has to be argued from the content, not from the
shape of other landing pages.

## Content that is not real

Numbers, testimonials, logos, avatars, security claims and case studies are real
and attributable, or they are not shown. A placeholder styled to look real is
worse than blank space, because the reader cannot tell.

When content is genuinely not available yet, label the gap where the reader can
see it, not only in a comment.

## Every state, not just the full one

An interface has an empty state, a loading state and an error state. A screen
that only works with three rows of ideal data is a third of a screen. The same
applies to both themes if a theme toggle ships, and to the narrow width.

## The keyboard and the finger

Tab reaches every control, focus is visible without a mouse, and nothing is
reachable by hover alone. Tap targets are large enough to hit, and far enough
apart to hit the right one.

Contrast is computed, not judged: grey on grey passes by eye and fails at 4.5:1.
If a pair is uncertain, calculate the ratio rather than asserting it.

## Delivering

Run it. Exercise every interactive element once — every button, link, form,
toggle, menu — and report what each one did. Then run the delivery gate:

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/deliver.mjs"
```

It re-scans the interface files changed in this session and records the result.
Until it has run, the session does not end: a claim that the interface works is
not evidence that it does, and the gate is built on the run rather than on the
sentence.

If it reports findings, fix them and run it again. Do not describe the output as
clean without reading it.
